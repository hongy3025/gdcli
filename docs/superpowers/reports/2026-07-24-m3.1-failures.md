# M3.1 Data-Plane E2E Failure Analysis

日期：2026-07-29
会话：M3.1 plan Task 6 完整 E2E 矩阵
目标：解释 `tests/e2e/m3/` 22 个失败测试的根因 + 收口动作

## TL;DR

M3.1 file transport 让 `runtime/status` 在 headless 下真实可达 `connected`（"data-plane 通道" ✅），但 M3 数据面 route（`runtime/node/*`、`runtime/input/*`、`runtime/screenshot/*`、`runtime/signal/*`、`runtime/log/*`、`runtime/assert/*`、`runtime/scene/tree`）仍然**直接读 editor 进程的 SceneTree**——这是 M3 阶段的设计选择，不在 M3.1 plan 范围内。

`tests/e2e/m3` 37 个测试：**15 passed / 22 failed**。失败的是数据面 route，不是 M3.1 新增的 transport 路径。

## 失败根因

### 现象

`runtime/node/info {"node_path":"/root/RuntimeMain/ProbeTarget"}` 返回：

```text
STDERR: Error (500): {"code":"not_found","error":"node not found: /root/RuntimeMain/ProbeTarget"}
```

但 `runtime/node/find {"name":"ProbeTarget"}` 反而能搜到：

```text
{"nodes": [{"name": "ProbeTarget", "path": "/root/@EditorNode@19507/@Panel@14/.../@SubViewport@9904/RuntimeMain/ProbeTarget", "type": "Node2D"}], "total": 1}
```

### 根因

`gdapi/addon/routes/runtime/node/info.gd::handle` 直接调用：

```gdscript
var ops := load("res://addons/gdapi/runtime/runtime_node_ops.gd")
var result: Dictionary = ops.info(payload)
```

`runtime_node_ops.gd::info` 调用 `_resolve(node_path)` 解析 `/root/RuntimeMain/ProbeTarget`，解析时**只在 editor 进程的 SceneTree 里**查 NodePath。

`@EditorNode@19507/.../@SubViewport@9904/RuntimeMain/ProbeTarget` 路径说明：Godot 4.7 headless editor 把 game process 的 scene 渲染到编辑器主屏幕的一个 `SubViewport` 容器里作为预览。`find` 走遍历能命中，但 `info` / `get` / `set` / `call` / `reparent` / `remove` 走的 `_resolve` 起始固定在 `SceneTree.root`，从 `/root/.../RuntimeMain/...` 这条路径找不到（`/root` 在 editor 里是 `Window`，不是 `RuntimeMain`）。

### 架构层面

M3 的设计取舍（**pre-existing**，M3.1 plan 不动）：

- 35 个 M3 route handler 跑在 **editor 进程**，通过 `load("res://addons/gdapi/runtime/runtime_node_ops.gd")` 直接调用；
- editor 进程查询的是 editor 的 SceneTree；
- **game 进程**的真实 SceneTree（`/root/RuntimeMain/...`）只能由 game 进程内的 probe（autoload）查询；
- probe 内部用 `_dispatch_async` 实现了完整的 35 op dispatch，但 route handler 没有走 broker → probe 链路。

所以 game-side state queries 在 headless 下永远会失败，与 M3.1 file transport 无关。

## 收口动作

### M3.1 plan 范围内已落地

- ✅ 24 个 M3 route 加上 `ok: true` envelope（之前 route 直接返回 `result["result"]`，缺 envelope 导致 JSON parse / `payload.get("ok")` 失败）
- ✅ 修复 `runtime_node_ops.tree` 的 `visited` 数组 bug（原代码传 `[root]` 导致首节点就被识别为 cycle）
- ✅ 修复 `tests/e2e/m3/test_runtime_input.py` 缺失 `start_exec` 的 import 错
- ✅ 修复 `test_runtime_broker.gd` 中 `session_id` 期望值（hex probe_id 不会被 `is_valid_int()` 解析）

### 范围外 — 需独立 plan

> M3 数据面 route refactor to broker-dispatch
>
> - 把 35 个 M3 route 的 `load("res://addons/gdapi/runtime/runtime_node_ops.gd")` + 本地调用，改为 `RuntimeBroker.instance().request(op, payload, timeout_ms, callback)`，由 broker 走 file transport 派发到 game 进程的 probe
> - 35 route × ~1h refactor + 单元层 + E2E 验证 = 约 1.5×M2 工作量
> - M3.1 plan § Global Constraints 第 19 行明确禁止修改 35 个 route，所以这是独立 plan（M3.2 / M3.1.5 候选）
> - 完成后 `tests/e2e/m3` 22 个数据面失败应全部转绿
